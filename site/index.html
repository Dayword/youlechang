01 / 背景与问题

园区客询的三个老问题

游乐园的日常咨询高度集中在票价套餐、项目身高年龄限制、办卡充值与退卡、失物招领、路线与周边。 原有「人工答疑 + 静态 FAQ」的组合有三个绕不过去的毛病：

答得不准

同一个问题，换个问法就匹配不到

「旋转木马多少钱」「木马多少钱一次」「坐一次转马要几个币」在关键词匹配下是三件事，静态 FAQ 只能命中第一条。

答得不全

知识散在多个文档里，靠人翻

价目、规则、活动、公告分别在不同文档中，人工客服需要跨文档检索，回复慢且口径容易不一致。

根本办不了

能问不能办，最后还是得去前台

「我卡里还有多少钱」「帮我退卡」「我丢了一个绿色水杯」——这些不是知识问答，而是要读写业务数据才能回答。

设计目标：一个既能「答得准」（检索召回不靠关键词硬匹配）、又能「真办事」（工具调用读写真实业务数据）、 并且「说得清」（给出可核验的来源与中间过程）的园区 AI 助手 —— 同时把整个门店运营搬进同一个后台。
02 / 系统架构

四层结构，一套后端供两端

小程序与 PC 后台共用同一个 FastAPI 服务与同一份数据库：游客侧走问答与自助办卡， 商家侧走知识库与经营分析。智能层由多个职责单一的 Agent 串成流水线，而不是一个巨型 prompt。

03 / 检索增强链路

从一句口语提问，到一条可核验的答案

五步流水线，每一段都可单独评测、单独替换。

问法归一：把口语提问映射到标准问法

先做意图路由（关键词快速通道 + 小模型兜底分类），再对问题做改写与归一， 让「坐一次转马要几个币」与知识库里的「旋转木马多少钱」落到同一语义位置。

RouterAgentQueryAgent硬超时保护

混合召回：关键词与向量各补各的短板

BM25（jieba 分词）擅长专有名词与价格数字的精确命中，向量（BGE-M3）擅长换问法后的语义相似。 两路并行召回，各自带候选数量上抛。

BM25 + jiebaMilvus + BGE-M3并行召回

分数融合：α 加权，且用消融数据定 α

两路分数按 α 加权融合。α 不是拍脑袋定的 —— 用独立的 α 扫描实验确定取值（见下方评测）。

HYBRID_ALPHA候选合并去重α 扫描实验

精排：只精排一次，且按长度截断

多路候选合并后一次性送 BGE-Reranker-v2-m3 精排，并按 160 字截断长块。 精排是整条链路最贵的一步，避免「每路各排一次」是提速的关键。

BGE-Reranker-v2-m3单次精排160 字截断

校验与生成：低幻觉约束 + 来源标注

用精排分阈值做免 LLM 校验（省掉一次模型调用），生成阶段强约束「只依据召回上下文作答」， 并按回答类型给出兜底话术与引用来源。

04 / 核心能力

八件事，都是实测过的

速度

天气问句 0 次 LLM 调用

纯天气问句（「明天要下雨吗」「今天适合去玩吗」）走规则模板直答，实测 0.16~0.36s（原走地图 Agent 需 3~10s）。给出的不是温度数字，而是园区出游结论：来不来、带不带伞、哪些室外项目受影响。

速度

问答缓存命中约 0.1s

检索与答案双缓存 + 知识库变更后失效重建，重复高频问题的响应压到百毫秒级。

能办事

账户管家 9 个工具

我的订单、卡明细、退卡资格核查、自助退卡、会员码、消费明细、我的收藏、园区公告、账号资料 —— 用户说一句就能查、能办。

能办事

失物招领的模糊匹配

「一个绿色的杯子」能匹配到已入库的失物，支持按颜色 / 类别 / 外观特征检索，游客可自助报失并进入统一库。

能办事

算得出「剩 120 币能玩什么」

把余额与项目价目表联立计算，而不是让用户自己对着价目表加总。

会记忆

服务端多轮 + 用户画像

会话存储与用户画像（年龄段 / 身高 / 关注点）落在服务端，换设备不丢上下文；回答后给出基于上下文的追问建议。

商家侧

经营小助手：说一句话就出报表

商家在后台说「看一下今天的营收汇总」，助手直接调用工具查库并渲染卡片与趋势图，不是「聊天」，是「办完再汇报」。

商家侧

知识库智能体

从问答日志里自动发现「没答上来」的问题 → 生成候选答案 → 过三道去重闸门后入库，形成知识闭环。

工程

统计口径单一真源

意图分布等统计在读侧用同一套意图识别函数实时聚合，不依赖写入时落库的字段，避免两套口径打架。

05 / 知识库治理

同一个业务问题，库里只能有一条答案

这是整个系统最重要的一条不变量。重复知识会让检索引擎把同一答案召回两次、挤掉真正相关的内容， 并让「来源标注」失去意义。治理不靠单一阈值，而是三道闸门加一次 LLM 裁决。

闸门一 · 生成侧

候选答案先过覆盖检查

知识库智能体从问答日志里收集「盲区」问题时，先比对已有知识，已被覆盖的不再生成候选答案，从源头少造重复。

闸门二 · 入库侧

所有写入必经，同问题跳过

无论是文档解析入库还是智能体回传，统一走同一道去重闸门；命中已有问题则跳过而不是覆盖， 并且整批只做一次 LLM 裁决以控制成本。园区原始权威来源享有豁免。

闸门三 · 检索侧

召回结果按问法归并

检索返回后按「问法」维度去重，确保呈现给用户和模型的上下文里，同一个问题只出现一次。

判据为什么不用向量阈值？实测下来纯向量相似度分不开：噪声样本就能到 0.75~0.80，而真正的重复也只有 0.88 左右 —— 阈值卡在中间必然误杀。因此流程定为「精确匹配 → 向量召回 → LLM 裁决」， 并且以「问法」为单位判断（优先读取块内标注的标准问法行），而不是比对整段正文。
