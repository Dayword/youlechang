## 二、作品简介候选（均 ≤300 字）

### 版本 A（推荐 · 299 字）—— 突出"能办事"

> 问题：游乐园咨询高频重复（票价/失物/办卡），人工坐席难覆盖；市面问答机器人只会念文档，查不了余额、核销不了券，游客仍要跑窗口。方案：鸭先知以多 Agent 编排为核心（意图路由→中央调度→混合检索 BGE-M3+BM25+Rerank→防幻觉生成），将 20 个园区/账户/工单/天气工具按需挂载，让 AI 真正查余额、算套票、登记失物；并以用户画像实现跨轮个性化。效果：常规问答由 28~41s 降至 4.7~8.1s，纯天气问句 0 次大模型、0.16~0.36s；零泄漏留出集端到端召回 0.9231、R@4 1.0000。应用：已落地游乐园，游客小程序+商家 PC 后台+员工核销端闭环。

### 版本 B（298 字）—— 突出算法链路

> 问题：游乐园咨询重复碎片化，传统客服与"文档问答"机器人无法回答需要查库的问题（余额够玩什么、券怎么退），更无法代办。方案：构建多智能体协同的问答与运营系统——意图路由后由中央调度统一编排，检索侧融合 BGE-M3 语义向量与 BM25 关键词并 Rerank 精排，生成侧以"必带参考资料"约束防幻觉；20 个园区工具按触发词按需挂载，使模型具备真实执行能力，并以服务端会话与用户画像实现个性化。效果：问答时延由 28~41s 降至 4.7~8.1s，天气类 0 次大模型、0.16~0.36s；零泄漏人工留出集端到端召回 0.9231。应用：已覆盖游客小程序、商家 PC 管理端与员工核销端。

### 版本 C（299 字）—— 稳妥平衡版

> 问题：游乐园服务痛点：咨询高频重复、人工成本高；通用问答机器人"只会说不会做"，无法查余额、核销游园券、登记失物，AI 与业务脱节。方案：鸭先知采用多 Agent 架构（意图路由→中央调度→混合检索→防幻觉生成），以 BGE-M3+BM25 融合并 Rerank 精排保证召回，将园区业务、账户管家、服务工单、天气四类共 20 个工具按需挂载，让 AI 能真实完成查余额、算套票、办卡、报失；端侧覆盖小程序、PC 后台与员工核销端。效果：常规问答由 28~41s 降至 4.7~8.1s，纯天气问句 0 次大模型（0.16~0.36s）；零泄漏留出集端到端召回 0.9231、R@4 1.0000。

## 四、使用注意

1. **字数口径**：以上字数按 Unicode 字符数统计（含标点、字母、数字），已逐条核算 ≤300 / ≤20。提交前建议在报名系统输入框里再确认一次（部分系统按"中文字数"口径统计，通常只少不多）。
2. **合规**：名称与简介均不含学校名称、Logo、指导教师信息，可直接对外。
3. **客户名与商标**：简介 A/C 写的"已落地游乐园"是刻意**不点名客户**。若要在任何材料里写出具体园区名（大黄鸭），属于第三方商标使用，需同时备好**合作意向书或试点应用证明**放进取证材料，否则采用当前表述。
4. **数据一致性**：简介里的 4.7~8.1s / 0.16~0.36s / 0.9231 / 1.0000 均取自本项目 `README.md`「测试与评测」「性能与延迟」两节实测，**方案书、PPT、视频中必须用同一组数字**，不要另起口径。
